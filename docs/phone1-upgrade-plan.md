# 手机 1 升级方案（0.1.1 / Room v2 → 0.1.16 / Room v4）

**状态：方案，未执行。** 本文只写"到时怎么做"，本轮不对手机 1 跑任何 adb 命令。
手机 1 当前是 `full 0.1.1 / versionCode 2`，Room 库 `version = 2`；0.1.16 是 `versionCode 17`，Room 库 `version = 4`。
覆盖安装时 Room 会自动依次执行 `MIGRATION_2_3`、`MIGRATION_3_4`（`AppDatabase.kt`），**没有反向迁移**：装上以后不能靠降级回 0.1.1 来"反悔"。

> 两台测试机不要混：本轮一直在动的 `6c3619c` 是手机 2（正式包 + 预览包都已升 0.1.16）。手机 1 的序列号在下面用 `<序列号>` 占位，执行前先 `adb devices` 核对。

---

## 0. 升级前：用户先在 App 里做的事（不做完不要装）

1. 打开手机 1 上的 GetMedia →「我的」→「数据备份」。
2. 点 **「立即备份」**，等到卡片显示 **「上次备份：N 首 · 时间」**（不是"上次备份失败"，也不是"还没备份过"）。
3. **记下两个数字**，写在哪里都行：
   - 卡片上的 **N 首**（这次云端清单备份的条数）；
   - 「存储空间」上的 **M 个条目保存在本机**（本机库条数）。
4. 抽查 1–2 条能正常播放（这是升级后要对比的样本）。
5. 保持手机电量 ≥ 30%，升级过程不要拔线、不要切账号。

**为什么必须先备份**：Room 迁移不可逆，而云端清单备份是"清单" Insurance——它能在库结构出问题后把元数据找回来（**不含媒体文件本体**，本体一直在 `files/audio`、`files/video` 下，`install -r` 不会清）。自动备份开关此刻是否开启都不影响这次手动备份。

---

## 1. 装前核对（只读取数，记录到执行记录里）

把 `<序列号>` 换成实际值。以下命令只读，不改手机数据。

```bash
adb devices                                   # 确认手机 1 在线，别打到手机 2
adb -s <序列号> shell "dumpsys package com.getmedia.app.full | grep -E 'versionName|versionCode|firstInstallTime'"
```

记录三项：

| 项 | 期望 / 记法 |
|---|---|
| `versionName` / `versionCode` | `0.1.1` / `2` |
| `firstInstallTime` | 记下原值，**装后必须不变** |
| 本机条目数 / 备份首数 | 用第 0 步用户记下的 `M` / `N` |

APK 用本轮归档的正式包（预览包不要装到手机 1）：

`local-artifacts/getmedia-apk/stage6-0.1.16-20261120/app-full-release.apk`
SHA-256 `2ebcf52c3442fc46e05ced558ac6cc000248738f3a7a2e3319e5f0b53350d2d8`

## 2. 安装（只用 install -r）

```bash
adb -s <序列号> install -r local-artifacts/getmedia-apk/stage6-0.1.16-20261120/app-full-release.apk
```

规矩：**只 `install -r`**。不要 `pm uninstall`，不要 `pm clear`，不要卸载后重装，不要另开第三个包名。
`-r` 保留现有数据与已经持久化的 SAF 目录授权；版本号从 2 跳到 17，Room 在首次打开数据库时自动连跳 v2→v3→v4。

## 3. 装后核对（装完先做这些，再登录）

```bash
adb -s <序列号> shell "dumpsys package com.getmedia.app.full | grep -E 'versionName|versionCode|firstInstallTime'"
```

| 核对项 | 判据 |
|---|---|
| 版本 | `0.1.16` / `17` |
| `firstInstallTime` | 与第 1 步**完全一致**；变了说明被清过数据，立刻停手报告 |
| 本机条目数 | App →「我的」→「存储空间」仍是第 0 步的 `M`（迁移只加列/加表，不删条目） |
| 播放抽查 | 用第 0 步那 1–2 条，确认能起播、进度正常 |
| 备份卡片 | 「上次备份：N 首 · 时间」还在；如果变成"还没备份过"，说明账号态/数据被清，停手 |
| 崩溃 | 启动后看 `adb -s <序列号> logcat -d | grep 'FATAL EXCEPTION'`，应为空 |

**任一判据不满足就停手**，不要继续登录、不要尝试"再装一次碰碰运气"。

---

## 4. 升级后首次登录会发生什么

按顺序（这是 `LibrarySyncRunner` / `LibrarySyncGate` 的既定行为，不是本次新加的）：

1. **先拉后推**。登录成功后先向服务器拉曲库清单，云端已有的行只补缺失（`insertIgnore`，不覆盖本机标题、收藏、类别、`localPath`）；本地已有文件但云端没有的先记下来。
2. **弹「上传本机新增」确认**。标题就是"上传本机新增"，正文是"有 N 条只在这台手机上，上传到账号 X？"。**这一步由用户自己点**：要传就点上传，不想传就点暂不上传（该账号以后不再问、也不自动传）。AI 不代点。
3. **隐私说明 v3**。若账号还没同意 v3，会先收到 `consent_required=true` 并弹同意页；在同意之前，同步的拉取和上传都是 0（客户端闸门会拦住）。同意 v3 之后上面两步才会真正发出请求。
4. **恢复决策卡**（如触发）。本地非空且云端有备份时，可能弹「恢复云端备份 / 用本机内容 / 稍后」。这也由用户自己选；选完之前自动备份是暂停的。

> 手机 1 是老版本直接跨到 0.1.16，云端清单备份与服务器曲库是两回事：前者在「数据备份」卡片，后者决定「云端未下载」标签。两者都不会因为 `install -r` 丢失。

---

## 5. 失败时怎么办（迁移不可逆，先保数据再排查）

**绝对不要做的事**：不要降级装回 0.1.1（没有 v4→v2 迁移，且旧 APK 读不了 v4 库）；不要 `pm clear`；不要卸载重装；不要在没备份的情况下手动改库文件。

按现象处理：

| 现象 | 处理 |
|---|---|
| 装上后起不来 / 闪退 | 停手。先确认第 0 步的云端备份存在；本机媒体文件没被清。把 `logcat` 与 `dumpsys package` 输出交给开发，**不要自行清数据重试**。 |
| 能启动但条目数少了很多 | 停手，不要登录触发同步。云端清单备份还在服务器上：登录后在「我的 → 数据备份 → 从云端备份恢复」里恢复（只补缺失，不覆盖已有条目）。 |
| 条目在、文件不在（列表显示"云端未下载"） | 用条目菜单的「下载到本机」逐条补，或在导出页用「先下载这 N 项」批量补；抖音行要本机直连解析，失败时如实记为失败，不要找用户要 Cookie。 |
| 登录时同意页/上传确认没出现 | 先看网络与账号档位（同步要求 owner + 隐私 v3）；不出现就不是失败，等条件满足后下一次前台/登录再问。 |

**手机 1 上现在有哪些可恢复的东西**：

1. **云端清单备份（最近 3 份）**：第 0 步手动点的那份 + 之前的自动备份。恢复元数据，**不含媒体文件本体**；
2. **服务器曲库清单与已存媒体**：`0.1.1` 时期已上传/已提取的条目，登录后可重新拉回；B 站行有服务器已存文件的可直接补下载；
3. **本机媒体文件本体**：一直在应用的私有 `files/audio`、`files/video` 里，`install -r` 与 Room 迁移都不碰它们。清单恢复后按原主键回填，收藏/分类/重命名一起保住。

只要没有 `pm clear`，这三样至少保住第 3 项；因此**清数据是这次升级唯一的真正不可逆操作**。

---

## 6. 执行时的停止点

- 第 0 步没做完（备份失败 / 数字没记）→ 不装。
- 第 3 步任一核对不过 → 不登录、不重试。
- 第 4 步的密码、上传确认、恢复决策卡 → 全部停下来由用户本人操作，AI 不代点、不读取或询问密码。
